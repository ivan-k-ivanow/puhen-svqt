# Пухен Свят — подробен отчет за работата и план до админ панела

Дата: 18 октомври 2026 г.

Днес направихме важна стъпка в развитието на „Пухен Свят“ — не просто продължихме да пренасяме сайта към React, а подобрихме структурата на целия проект, като отделихме backend-а от frontend-а. Това е важно, защото искаме да изградим поддържаем проект, който впоследствие да може да се развие от онлайн каталог към пълноценен онлайн магазин.

## 1. Какво свършихме днес

### Задача 1. Подобрихме архитектурата на проекта

Преди работехме по backend-а, а сега го отделихме в собствена папка `server/`. След това създадохме отделна папка `client/` за React приложението.

Новата структура разделя двете основни части на приложението:

- Server — backend логиката, API маршрутите, услугите и работата с базата данни.
- Client — потребителският интерфейс, който се изпълнява в браузъра чрез React.

Структурата на проекта вече изглежда така:

```
puhen-svqt/
│
├── server/
│   ├── src/
│   │   ├── config/
│   │   ├── controllers/
│   │   ├── middlewares/
│   │   ├── repositories/
│   │   ├── routes/
│   │   ├── services/
│   │   ├── validators/
│   │   └── utils/
│   │
│   ├── package.json
│   └── package-lock.json
│
├── client/
│   ├── src/
│   │   ├── components/
│   │   ├── pages/
│   │   ├── assets/
│   │   ├── styles/
│   │   ├── App.jsx
│   │   └── main.jsx
│   │
│   ├── package.json
│   └── package-lock.json
│
├── prisma/
├── generated/
├── .env
├── prisma.config.ts
└── tsconfig.json
```

Това е обобщена структура на проекта; не всички показани подпапки и файлове означават, че вече са създадени или завършени.

Запазихме в root директорията конфигурацията, свързана с Prisma, генерирания клиент, променливите на средата и TypeScript. Така не преместихме всичко механично, а запазихме необходимите файлове на правилното ниво за текущата конфигурация.&#x20;

Защо тази промяна е важна?

1. Backend и frontend имат ясно разграничени отговорности.
2. Можем да развиваме React клиента, без да смесваме UI кода със сървърната логика.
3. По-лесно ще организираме зависимостите и командите за стартиране на двете приложения.
4. Ще можем да изграждаме админ панела върху съществуващия backend, вместо да дублираме логиката за работа с продуктите.
5. Подготовката за бъдещ онлайн магазин ще бъде по-лесна, защото клиентът ще комуникира с backend-а чрез API.

### Задача 2. Запазихме архитектурата на backend-а

Продължаваме да следваме познатия от SoftUni модел:

```
Route
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
Prisma
  ↓
PostgreSQL
```

Всеки слой има собствена отговорност:

| Слой         | Отговорност                                                       |
| ------------ | ----------------------------------------------------------------- |
| Routes       | Определят API маршрутите и свързват заявките с контролерите.      |
| Controllers  | Обработват HTTP заявките и оформят отговорите.                    |
| Services     | Съдържат бизнес логиката.                                         |
| Repositories | Изолират заявките към базата данни.                               |
| Prisma       | Осигурява достъп до PostgreSQL.                                   |
| Validators   | Проверяват входящите данни.                                       |
| Middlewares  | Обработват общи задачи като удостоверяване и обработка на грешки. |

Целта е React клиентът да използва API, а не да комуникира директно с базата данни. Така и публичният сайт, и бъдещият админ панел ще могат да използват същата сървърна логика.

### Задача 3. Създадохме React клиента с Vite

Създадохме отделна `client/` папка и инициализирахме React приложение с Vite.

Проверихме, че приложението се стартира успешно.

Това е важна основа: вече имаме отделно място за frontend разработката, вместо да смесваме React файловете със сървърния код.

### Задача 4. Планирахме структурата на React клиента

Организираме компонентите и страниците отделно, така че да могат да се използват повторно и да се поддържат по-лесно.

```
client/src/
│
├── components/
│   ├── header/
│   │   ├── Header.jsx
│   │   └── Header.css
│   │
│   ├── footer/
│   │   ├── Footer.jsx
│   │   └── Footer.css
│   │
│   └── products/
│       ├── ProductCard.jsx
│       └── ProductFilters.jsx
│
├── pages/
│   ├── home/
│   │   ├── Home.jsx
│   │   └── Home.css
│   │
│   └── product-details/
│
├── assets/
├── styles/
│   ├── global.css
│   └── variables.css
│
├── App.jsx
└── main.jsx
```

Това е работната структура, която развиваме, а не окончателен списък на всички съществуващи файлове.

Уточнихме и принцип за стиловете:

- CSS за конкретен компонент или страница се намира близо до него.
- Общите стилове и CSS променливите се държат централизирано.
- Избягваме един огромен CSS файл, в който стиловете на различни страници се застъпват.

### Задача 5. Продължихме работата по продуктовите компоненти

Работихме по `ProductCard.jsx` и `ProductFilters.jsx`.

Идеята е продуктовата карта да отговаря за визуализирането на един продукт, а филтрите — за избора на категория. Това ни позволява да поддържаме каталога по-лесно и да не повтаряме един и същ JSX код.

Продължихме и работата по продуктовите детайли, включително показването на информацията и снимките на конкретния продукт.

### Задача 6. Подредихме CSS файловете

Разделихме стиловете между:

- `styles.css` — общите стилове.
- `products.css` — стиловете за продуктовата част.

След това променихме форматирането, така че CSS правилата да са компактни и четими, без празни редове между свойствата.

Стиловете все още не са окончателно завършени. Ще продължим с конкретни корекции след като основните функционалности на клиента са готови.

## 2. Какво остава да направим по React клиента

Основните оставащи функционалности, които уточнихме, са hamburger менюто, галерията на Product Details и image modal.

### Етап 1 — Hamburger меню

Цел: завършена мобилна навигация

Ред на работа

- Преглеждаме текущите `Header.jsx`, `Header.css` и навигационните класове.
- Проверяваме дали бутонът за hamburger меню вече има React state.
- Добавяме или довършваме отварянето и затварянето на менюто.
- Свързваме всички навигационни линкове.
- Затваряме менюто след избор на линк и при навигация.
- Проверяваме поведението на мобилни и десктоп екрани.

Критерий за завършване: менюто работи с реалните маршрути, отваря се и се затваря правилно и не пречи на останалата част от страницата.

### Етап 2 — Галерия на продуктовата страница

Цел: правилно показване на всички снимки

- Проверяваме как backend API връща снимките на продукта.
- Показваме основната снимка.
- Показваме миниатюри за останалите снимки.
- При клик върху миниатюра сменяме основната снимка.
- Обработваме продукт с една снимка или без допълнителни снимки.
- Проверяваме оформлението на галерията на мобилно и десктоп.

Критерий за завършване: посетителят може да разглежда всички снимки на продукта, а избраната снимка се показва правилно.

### Етап 3 — Image modal

Цел: отваряне на голям изглед на снимката

- Отваряме modal при клик върху основната снимка.
- Показваме правилната избрана снимка.
- Добавяме бутон за затваряне.
- Позволяваме затваряне с Escape.
- Обработваме клик извън изображението, ако това е част от дизайна.
- Не затваряме modal при клик върху самото изображение.
- Проверяваме размерите и скролването на мобилни устройства.

Критерий за завършване: modal работи с галерията и винаги показва правилната снимка.

Препоръчителният ред е галерията преди modal, защото modal трябва да работи с избраната снимка от галерията. Така няма да дублираме състояние и логика.

## 3. След функционалностите — финално тестване на клиента

След като трите задачи са завършени, ще проверим целия публичен сайт.

| Област            | Какво трябва да проверим                                                        |
| ----------------- | ------------------------------------------------------------------------------- |
| Начална страница  | Всички секции се зареждат и линковете работят.                                  |
| Каталог           | Продуктите се зареждат от API и се показват правилно.                           |
| Филтри            | Изборът на категория показва правилните продукти.                               |
| Product Card      | Снимка, име, цена и преминаване към детайлите.                                  |
| Product Details   | Зарежда се правилният продукт и неговите данни.                                 |
| Галерия           | Сменя основната снимка според избраната миниатюра.                              |
| Image Modal       | Отваря и затваря големия изглед правилно.                                       |
| Header            | Desktop навигацията и hamburger менюто работят.                                 |
| Responsive дизайн | Проверяваме мобилния изглед, включително заглавията на продуктите.              |
| API и грешки      | Проверяваме заявките, грешките в конзолата и обработката на невалидни отговори. |

CSS няма да се преработва изцяло отново. Ще отстраняваме конкретните проблеми, които открием при тестовете.

## 4. Подготовка преди админ панела

Когато публичният клиент премине проверките, ще направим кратък технически преглед на backend-а, преди да добавяме административни функционалности.

1. Проверяваме текущите routes, controllers, services и repositories.
2. Проверяваме продуктовия модел в Prisma и връзките му със снимките и категориите.
3. Проверяваме API отговорите, които React клиентът използва.
4. Проверяваме съществуващото удостоверяване и защитата на маршрутите.
5. Планираме административните операции според вече съществуващата архитектура.

След това започваме админ панела с последователни задачи: вход, dashboard, списък с продукти, добавяне, редактиране, изтриване и управление на изображенията.
